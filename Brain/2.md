# Problem Statement: AI Agent Permission & Audit Layer

## The Problem

Organizations are rapidly deploying AI agents that don't just answer questions — they **take real actions**: processing refunds, updating customer records, modifying databases, calling internal APIs, approving requests.

But as agentic AI adoption accelerates, a critical governance gap has emerged:

1. **No fine-grained control** — Most systems either trust the AI agent completely or rely on brittle, hardcoded if/else checks buried in application code. There's no scalable, declarative way to define _exactly_ what an agent is allowed to do, under what conditions, for which resources.

2. **No audit trail** — When an agent takes an action (or is blocked from taking one), there's typically no immutable, queryable record of _why_ that decision was made. This makes it nearly impossible to answer basic compliance and security questions after the fact: "What did this agent do in the last hour?" "Why was this specific action denied?" "Can we prove this agent never touched data it shouldn't have?"

3. **No separation between reasoning and authorization** — The AI model that decides _what to try_ and the system that decides _what's allowed_ are usually the same thing, or not clearly separated. This is a security anti-pattern: the entity generating an action shouldn't also be the sole entity deciding whether that action is permitted.

This isn't a hypothetical problem — it's the exact gap AWS itself is actively building tooling for (Cedar, the policy language behind Amazon Verified Permissions, exists specifically to solve fine-grained authorization at scale). As more companies move from "AI that talks" to "AI that acts," this becomes a blocking issue for production deployment, not an edge case.

## Our Solution

We built a **permission-enforcement and audit layer that sits between an AI agent's decisions and real-world execution**:

- **Agent (Strands Agents SDK + Amazon Bedrock)** — reasons about tasks and proposes actions using tool-calling
- **Policy Engine (Cedar)** — every proposed action is evaluated against explicit, human-readable policies _before_ execution. Cedar returns ALLOW or DENY with a traceable reason — the agent's reasoning and the authorization decision are cleanly separated.
- **Audit Log (OpenSearch)** — every decision, allowed or denied, is written to an immutable, searchable log: what was attempted, when, by which agent, and why it was allowed or blocked.
- **Sandboxed backend (AWS SAM)** — simulated resources (e.g. a records database) the agent acts on, so the demo shows real actions being gated in real time, not just a chatbot.

## Why This Matters

This is the difference between "an AI that can chat about your data" and "an AI that can safely act on your data with proof of compliance" — which is precisely the trust gap standing between today's AI agent hype and real enterprise adoption.
